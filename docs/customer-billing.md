# 客户计费与人工充值

2026-10-23：原生 Sub2API 是唯一资金及调用扣费账本。网站不另扣一次，统一以 USD 额度展示。客户按原生模型基准金额的 0.5×结算，普通输入、缓存读取/写入、输出分别计价。

## 运营流程

1. 网站管理员登录，在“管理员实验室 → 客户计费与充值入账”选择客户。尚未创建接入 Key 的客户须先创建 Key，建立独立原生身份。
2. 开通该客户的 0.5×计费。只移除初始的 1 美元免费准入占位值；其他已有余额须人工核对。历史免费使用不追扣，已有人民币待启用金额不自动兑换。
3. 实际收款后填写唯一订单号、实收金额及币种、对应的入账美元额度，勾选确认后入账。页面显示所选客户的余额、消费和已入账总额。
4. 客户在“我的用量”查看余额、开通后已消费、已确认入账、每页 20 笔调用和充值订单。多把外部 Key 合并至同一客户账本。

订单号全局唯一，8–80 位字母、数字、点、横线或下划线。金额最多两位小数，入账 USD 0.01–100000。超时应重试相同订单号及金额，不能更换订单号。后台保存 pending 再调用固定原生充值码；码长限制为 32，避免底层数据库拒绝。

收费开通持有该客户的排他锁；桥接调用持有共享锁直到流式响应关闭。开通途中桥接拒绝调用。原生通用用户更新接口会忽略 balance，因此使用专门的余额调整接口清除测试占位值，读回确认余额归零和各组倍率 0.5 后才标记 active。流程失败可安全重试。

## 2026-10-23 验收

- Linux 26 项相关 Python 测试通过：客户隔离、接口鉴权、余额开通、故障恢复、幂等入账、调用锁及桥接；网站 19 项 Python 认证/订阅测试、19 项 Node 页面测试通过。
- 独立验收账号，未实际收款：原生账本入测试额度 $0.10；网页另入测试额度 $0.01。两笔均标记 QA / NO PAYMENT，重复提交不重复入账。
- GPT-6.1 Sol / low 的真实流式调用收到 response.completed：17 普通输入、0 缓存、5 输出 Token；基准 $0.000084，倍率 0.5，实际扣 $0.000042。余额从 $0.10 变为 $0.099958，与原生账单 ID 619 完全相等。
- 开通后余额为 0 时、消费后清退剩余测试额度再次归零时，均 HTTP 403 / INSUFFICIENT_BALANCE；拒绝没有新增账单或消费。验收结束暂停测试账号并保留账本。
- 隔离的本地网站数据库连接真实云账本，浏览器验证管理员充值、重试、客户读取及客户充值越权 403；1440px 与 390px 截图检查通过，无页面横向溢出或 JavaScript 错误。此项不等于 Render 生产发布验证。
- 真实测试发现并修复两个底层兼容问题：用户更新忽略余额、充值码数据库长度 32。首轮失败测试身份已暂停并保留审计。

## 当前边界

人工确认收款，不接支付渠道自动回调。人民币/欧元由管理员明确登记美元额度，不自动换汇。原生已入账变动为权威；页面“已确认入账”汇总本流程完成的订单，外部手动调账不伪装成充值订单。

余额准入由原生网关执行；在途调用完成后结算可能使余额小额为负，后续调用被拒绝。本轮真实付费模型仅验证 GPT-6.1 Sol 文本；七模型价格均已核查存在且非零，其余模型、缓存命中、流式取消及并发透支未逐一进行真实收费试验。

现有客户保持原免费配置，管理员逐个开通收费。上线回退先暂停新增收费开通/入账，保留 private/billing、原生用户/用量/充值码；不得以代码回退清除财务数据。
